================================================================================
WHY GREEDY ALWAYS FAILS HERE — THE DEPENDENCY STRUCTURE
================================================================================

The smell graph for this class looks like this:

  GC ──(+)──► [resolves Feature Envy between GC and LM]
  GC ──(-)──► LM   (Extract Class may produce new Long Methods in the extracted class)
  GC ──(-)──► II   (extracted class still calls private fields of parent → Inappropriate Intimacy)
              └─ this neg-dep ONLY fires when LM already exists in the class
                 (structural precondition: long orchestration methods are present to be moved)

  LM ──(+)──► [resolves Feature Envy between LM and GC]
  LM ──(+)──► [may resolve co-located Dup Code]
  LM ──(-)──► LM'  (Extract Method may produce another Long Method if extraction is partial)
  LM ──(-)──► LPL  (extracted helper methods may need extra parameters)
              └─ these neg-deps are weak: they fire only if the method is very long
                 and extraction splits responsibilities poorly

  LPL ──(+)──► DC  (Merge Parameter resolves Data Clumps across callers)
  LPL ──(-)──► DataClass  (Parameter Object may become a data-only class)

Key structural fact: GC's negative dependencies toward LM and II have a
PRECONDITION — they only fire if Long Methods already exist in the class.
This is state-dependent: once LM is resolved first, GC's neg-deps are suppressed.

This is the core trap for greedy. Here is why greedy always steps into it:

  1. GC and LM both have HIGH severity (3). Both get the same pos_out count (1
     each, pointing at each other's Feature Envy). Both get the same neg_out (2).
     Result: PD(GC) = PD(LM) = 0.5*3+1-2 = 0.5.

  2. Greedy must break the tie somehow — by insertion order, alphabetical, or
     index. GC appears first in the SonarQube output (class-level rules are
     reported before method-level). So greedy picks GC.

  3. Even if the tie were broken in favour of LM (lucky choice), greedy still
     fails in a different class configuration: if GC had one extra positive
     co-located edge (e.g. also co-located with a Data Clump), its PD would
     become 0.5*3+2-2 = 1.5 while LM stays at 0.5. Greedy would then pick GC
     deterministically — and still step into the same neg-dep trap.

  4. Greedy has no mechanism to look at what happens AFTER step 1. It only
     scores the current state. It cannot detect that picking GC now will raise
     h from 8 to 10 — i.e. make the situation worse before it gets better.

BFS explicitly simulates all three possible first steps and measures the
resulting h. It sees:
  - GC first → h goes up to 10 (bad)
  - LM first → h drops to 5 (best)
  - LPL first → h drops to 6 (ok but not optimal)
And selects LM. After LM is gone, GC's neg-dep precondition is no longer met,
so Extract Class runs cleanly with 0 new smells.

================================================================================
SMELL DEPENDENCY MAP (Markovič & Polášek rules, as used in the system)
================================================================================

Positive dependencies (refactoring A may RESOLVE smell B as side effect):
  Long Method / Complex Method  →  Feature Envy, Dup Code, Long Param List
  God Class / Large Class       →  Feature Envy, Data Clumps
  Long Param List               →  Data Clumps
  Dup Conditions                →  Divergent Change

Negative dependencies (refactoring A may INTRODUCE smell B):
  Long Method / Complex Method  →  Long Method (partial extraction), Long Param List
  God Class / Large Class       →  Long Method, Inappropriate Intimacy, Data Class
  Long Param List               →  Data Class
  Dup Conditions                →  Large Class

State-dependence of negative edges:
  The neg-dep "GC → LM" fires only if the class already contains Long Methods
  that will be pulled into the extracted class verbatim. If Long Methods are
  resolved first (Extract Method shrinks them), the extracted class receives
  short focused methods — the neg-dep does not materialise.

  Similarly "LM → LPL" fires only if the extracted helper needs to receive
  data from the original method via parameters. If the method is short and
  self-contained, no extra parameters are needed.

This state-dependence is what makes ordering matter and what makes greedy
provably suboptimal: it scores smells in isolation without modelling how
resolving one smell changes the firing conditions of another's neg-deps.
