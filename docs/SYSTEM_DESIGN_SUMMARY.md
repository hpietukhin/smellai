### Agent descriptions

#### A0: Test coverage verification
- **Function**: Verifies test coverage for code targeted by refactoring
- **Capabilities**: Auto-detects Maven/Gradle, executes tests, parses XML reports
- **Called by**: Workflow initialization and A6 (behavior preservation)
- **Calls**: A7 if tests are missing

#### A1: Code smell detection
- **Function**: Detects 8 types of code smells with severity levels
- **Method**: SonarQube static analysis via Docker container
- **Output**: Normalized smell detections with location and severity

#### A2: Developer query (planned)
- **Function**: Query developer for which smells to address
- **Method**: Interactive prompt or pre-configured priorities

#### A3: Smell prioritization
- **Function**: Calculates refactoring priority using dependency graph analysis
- **Formula**: `PZ_i = Severity_i + Σ(w_impact for each positive dependency)`
- **Output**: Prioritized sequence and visualization graphs (NetworkX)

#### A4: Refactoring prompt preparation (planned)
- **Function**: Prepares refactoring prompts from prioritized list
- **Method**: Retrieves from prompt database or generates based on smell type

#### A5: Refactoring execution
- **Function**: Applies refactorings in priority order using LLM reasoning
- **Method**: Maps refactorings to code hunks, generates refactored code
- **Runs in**: Loop over prioritized smell list

#### A6: Behavior preservation verification
- **Function**: Validates refactorings preserve code behavior
- **Method**: Reuses A0's test execution capabilities
- **Action**: Runs tests after each refactoring, calls A7 if tests not found

#### A7: Test generation (planned)
- **Function**: Generates tests for uncovered code
- **Called by**: A0 or A6 when test coverage insufficient

## Priority calculation formula

```
PZ_i = Severity_i + Σ(w_impact for each positive dependency)
```

Where:
- Severity: HIGH=3, MEDIUM=2, LOW=1
- w_impact = 2 per positive dependency
- Greedy selection: max(PZ) at each iteration

## Dependency rules

### Positive dependencies (Solving)
- Long Method → Switch Statement, Duplicated Code, Feature Envy, etc.
- Large Class → Data Clumps, Feature Envy, Bad Class Content
- Long Parameter List → Data Clumps

### Negative dependencies (Risk)
- Long Parameter List → Data Class
- Large Class → Long Method, Data Class, Inappropriate Intimacy
- Complex Method → Long Method, Long Parameter List

## Complete workflow

1. **A0**: Check test coverage for target codebase → Call A7 if tests missing
2. **A1**: Scan commit with SonarQube → Detect smells with severity levels
3. **A2**: Query developer for smell selection (planned, currently auto-selects)
4. **A3**: Analyze dependencies → Calculate PZ scores → Generate priority sequence
5. **Visualization**: Create dependency graphs (NetworkX)
6. **A4**: Prepare refactoring prompts (planned, currently generated inline)
7. **A5**: Apply refactorings in priority order (loop)
8. **A6**: Run tests after each refactoring → Verify behavior preserved
9. **Metrics**: Calculate code quality improvements
10. **MLflow**: Log all results for analysis

## Key innovation

The system implements a **dependency-aware prioritization** strategy based on Markovič & Polášek's theory, where refactoring order is optimized to:
1. Maximize positive cascading effects (solving multiple smells)
2. Minimize negative side effects (creating new smells)
3. Prioritize high-severity smells with high impact

This is visualized through NetworkX graphs showing green edges (positive dependencies) and red edges (negative dependencies).
