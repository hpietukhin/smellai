Spec-first reading: what the thesis says this system is

Spec summary

  • A multi-agent system for dependency-aware code smell refactoring.
  • Combines SonarQube smell detection, a Best-First Search planner, and LLM refactoring agents.
  • Targets Java code smells and evaluates with RefactoringMiner 2.0 and SWE-Refactor.
  • Logs intermediate states, LLM responses, and metrics to MLflow.

What this repository is about, precisely

Primary research concern

Evaluate whether AI agents can map or generate refactorings while respecting code smell dependencies and preserving behavior.

  • RMiner track: map known refactorings to diff hunks.
  • SWE track: generate refactored Java code and verify compile/tests.
  • Composite track: iteratively detect smells, prioritize them, select the next one, refactor, verify, and re-scan.

Spec pipeline (A–J) vs current code

Spec A–J from PDF

  1. A: load source, detect build system
  2. B: check if every function has tests
  3. C: generate missing tests
  4. D: run full baseline tests
  5. E: construct inter-smell dependency graph
  6. F: SonarQube smell scan
  7. G: developer selects target smells
  8. H: BeFS planner produces ordered plan
  9. I: LLM executes planned refactoring
  10. J: tests after refactor, rollback/replan

Every coding-agent step, described as data movement

RMiner agent

  • State source: workflow reconstructs an RMiner EvalSample.
  • Prompt assembly: code file, refactoring descriptions, diff hunk spans, optional smell context.
  • Model step: LLM predicts mapping JSON.
  • State sink: predictions emitted to MLflow scorers.

SWE basic agent

  • a0_setup: dataset record → checked out local repo state.
  • a5_generate: repo state + record → prompt → candidate Java code.
  • a6_verify: candidate code → filesystem mutation → compile/test result.
  • retry loop: compile errors are fed back into the next prompt.

SWE composite planning side

  • a1_detect_smells: local project → SmellEvent[].
  • a2_prioritize_smells: smell events → dependency graph + ordered queue.
  • a3_select_next_smell: queue → current smell_id.
  • a4_map_smell_to_refactoring: smell type → refactoring type heuristic.

SWE composite execution side

  • a5_generate: current smell context appended to prompt.
  • a6_verify: code applied; if compile succeeds, re-scan smells.
  • diffing: before-smells vs after-smells → resolved/created/persistent.
  • analytics: attempt, token usage, smell events, and git diff persisted.

Important Python models and contracts

Normalized sample contract

EvalSample is the repo’s lingua franca. It lets the workflows treat RMiner and SWE similarly even though their raw schemas differ.

Composite runtime contract

SWEEvalState is the richest state object in the repo: source record, workspace paths, refactoring artifacts, smell graph/queue, counters, Sonar config, persistence handle, and token tracking.

RMiner runtime contract

RMinerEvalState is intentionally smaller: this agent is a single-step mapper, not an iterative planner/executor.

Persistence contract

SQLModel tables in swe_refactor/persistence/models.py provide the replayable execution memory that powers visualization and analysis.

Notable findings, mismatches, and risks

Spec alignment gaps

  • The PDF says BeFS planner; code visibly centers on heuristic prioritization and iterative selection.
  • Developer selection stage from the paper is not a clear first-class runtime component in current Python.
  • Test generation stages B/C are described in the paper but are not a strong implemented path in this repo snapshot.

Code-level practical gaps

  • swe_refactor/smell_detection/ is almost empty in the tree, but composite agent imports utilities from it; either generated elsewhere or incomplete in this checkout.
  • The repo mixes research prototype code, evaluation flows, and dashboards; some paths look more mature than others.
  • The largest agent file (agents/swe_eval/agent.py) is doing many responsibilities at once.
If you want a “source of truth” runtime narrative, prefer: PDF theory for intended architecture + workflows/eval_workflow.py and the two LangGraph agent files for actual implemented execution.
